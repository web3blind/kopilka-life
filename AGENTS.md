# AGENTS.md — Копилка жизни

## Назначение проекта

`kopilka-life` — проект Telegram Mini App + бота “Копилка жизни”.

Цель: помочь человеку мягко замечать и накапливать действия, которые поддерживают жизнь: сон, здоровье, радость, благодарность, дела, мечты, отдых и честные итоги.

Проект должен быть простым, тёплым и практичным. Не превращать счастье в KPI, обязанность, марафон или источник вины.

## Ключевая идея

Пользователь пополняет “Копилку жизни” быстрыми конкретными действиями. За действия начисляется актив **ЖИЗНЬ**.

**ЖИЗНЬ** нужна для наглядности и радости от прогресса: человек видит, что маленькие действия складываются. Это не KPI, не рейтинг, не “оценка успешности” и не показатель ценности человека.

Продуктовая формула:

> “Копилка жизни” — мини-приложение в Telegram, где человек за 10 секунд в день пополняет личную копилку ЖИЗНИ: сном, движением, радостью, благодарностью, делами, добрыми делами, честными шагами и шагами к мечтам. Недельный договор заботы помогает выбрать мягкую цель и увидеть итог без наказания: при выполнении человек разблокирует подарок себе, а если цель оказалась слишком сложной — может честно закрыть неделю и упростить следующий договор.

## Главные принципы

1. **Мягкость важнее дисциплинарного давления.**
2. **Нет наказаний за пропуск.**
3. **Нет streak как центральной механики.**
4. **Нет “ты провалился”.**
5. **Тяжёлый день — тоже валидная запись.**
6. **Текст/голос — опциональны. Базовое действие должно быть кликом.**
7. **Деньги не хранятся в приложении в MVP.**
8. **Система фиксирует заботу, честность и видимый прогресс, а не измеряет ценность человека.**
9. **Интерфейс должен быть доступным для screen reader.**
10. **В простое backend должен почти не потреблять CPU.**

## Архитектура MVP

Один лёгкий Node.js сервис:

- отдаёт static frontend Mini App;
- предоставляет backend API;
- валидирует Telegram Mini App `initData`;
- принимает Telegram bot webhook;
- отправляет напоминания через scheduler;
- хранит данные в SQLite.

Frontend:

- без React, Next, Vue и других тяжёлых frontend-фреймворков;
- обычные `index.html`, `styles.css`, `app.js`;
- семантический HTML;
- все кнопки настоящими `<button>`;
- минимальный JS.

Backend:

- Node.js;
- Express или Fastify;
- SQLite;
- Telegram Bot API через webhook;
- scheduler не чаще раза в минуту;
- без long polling;
- без частых CPU-heavy циклов.

## Основной функционал будущего приложения

### 1. Telegram bot

Минимальные команды:

- `/start` — объяснить идею и дать кнопку “Открыть Копилку жизни”.
- `/today` — коротко показать сегодняшний баланс и кнопку Mini App.
- `/week` — показать недельный итог или кнопку открытия Mini App.
- `/settings` — напоминания и время.

Бот не должен быть основным интерфейсом для всех действий. Его роль:

- вход в Mini App;
- напоминания;
- короткие итоги;
- мягкие nudges.

Технические правила:

- использовать webhook, не polling;
- не держать несколько bot процессов;
- логировать ошибки без спама;
- не отправлять markdown, если можно обойтись plain text;
- все Telegram API ошибки логировать с полным сообщением.

### 2. Telegram Mini App

Главный интерфейс.

Основные экраны MVP:

1. Главная.
2. Пополнение Копилки.
3. История недели.
4. Недельный договор заботы.
5. Настройки.

#### Главная

Показывает:

- общий баланс ЖИЗНИ;
- баланс за сегодня;
- активный недельный договор;
- быстрые кнопки пополнения;
- короткий мягкий текст дня.

#### Пополнение Копилки

Быстрые категории:

- сон;
- движение;
- еда/вода;
- радость;
- благодарность;
- важное дело;
- шаг к мечте;
- доброе дело;
- честный шаг;
- отдых;
- сложный день.

Каждая категория — это конкретное действие. Под кнопкой показывается короткое описание того, что можно отметить (например: “Доброе дело — помощь, спасибо, тёплое слово”). Описание читается и экранным диктором.

Каждая категория создаёт запись `entry` с количеством ЖИЗНИ.

Опционально:

- короткая заметка;
- позже можно добавить голос, но не в MVP.

#### История недели

Показывает:

- записи по дням;
- сумму ЖИЗНИ за неделю;
- категории, которые встречались чаще;
- дни без давления и без красных “провалов”.

#### Недельный договор заботы

Поля:

- название цели;
- период недели;
- критерий выполнения;
- сумма фонда заботы;
- валюта: RUB / USDC / другое текстом;
- подарок себе при выполнении;
- направление перевода при невыполнении;
- статус.

Статусы:

- active;
- completed;
- not_completed_donated;
- too_hard;
- cancelled.

Закрытие договора:

- “Выполнил и подарил себе”;
- “Не выполнил и отправил в фонд”;
- “Цель была слишком сложной”;
- “Отменить без наказания”.

### 3. Напоминания

MVP:

- вечернее напоминание;
- пользователь выбирает время;
- пользователь может выключить напоминания;
- scheduler проверяет due reminders не чаще раза в минуту;
- отправка должна быть idempotent: не слать дубль, если `sent_at` уже есть.

Тон напоминаний:

Хорошо:

> Если есть силы, можно за 10 секунд пополнить Копилку жизни.

Плохо:

> Ты ещё не выполнил практику.

### 4. Баланс ЖИЗНИ

Рабочая логика начислений:

- благодарность: +1;
- радость: +1;
- отдых: +1;
- тяжёлый день, но честно отметил: +1;
- движение: +2;
- важное дело: +2;
- шаг к мечте: +2;
- доброе дело: +1;
- честный шаг: +2;
- нормальный сон: +3;
- выполненный недельный договор: +10;
- невыполненный договор + честный перевод/отчёт: +3;
- невыполненный договор без отчёта: 0.

Правило: баланс не должен использоваться для стыда. Это не рейтинг человека, а наглядный след того, что пользователь сегодня поддержал жизнь, сделал живое действие или честно заметил день.

### 5. Финансовая механика

MVP не хранит деньги и не подключает платежи.

Приложение только фиксирует:

- какую сумму пользователь сам назначил;
- что он обещал сделать;
- что он выбрал при успехе;
- куда он обещал отправить деньги при невыполнении;
- какой итог он сам отметил.

Запрещено в MVP:

- принимать средства;
- хранить приватные ключи;
- инициировать crypto transfers;
- обещать доходность;
- использовать механику азартных ставок.

Позиционирование: не “ставка”, не штраф и не азартная механика, а **договор заботы**. Денежные поля в MVP — только опциональное напоминание о намерении; главный смысл договора — мягкая цель, подарок себе, честный итог и возможность упростить следующую неделю.

### 6. Compass/happy слой

Идеи из `happy` и `compass` используются как слой подсказок, недельного разбора и мягких текстов, а не как замена основной механики.

Правила:

- быстрые кнопки остаются конкретными действиями, а не абстрактными итогами;
- не добавлять категорию “Достаточно на сегодня” в ряд действий — это тон завершающего статуса, а не действие;
- можно использовать формулировки “этого уже достаточно, если сил мало” после пополнения или в подсказке дня;
- подсказки могут мягко разделять “реальный сигнал” и “тревожный шум”, но без длинного дневника и без обязанности отвечать;
- практики должны занимать 1–15 минут и не превращаться в streak, отчёт или моральный урок;
- названия категорий и практик должны быть конкретными действиями, понятными без описания (не “добрый след”, а “доброе дело”; не “честный маленький шаг”, а “честный шаг”).

## Тон интерфейса

Писать коротко, тепло, без давления.

Примеры хорошего тона:

- “Что сегодня пополнило жизнь?”
- “Можно отметить одну маленькую вещь.”
- “Тяжёлый день тоже можно просто зафиксировать.”
- “Копилка пополнилась.”
- “Цель была слишком сложной — это тоже полезный вывод.”

Избегать:

- “Ты провалился.”
- “Ты потерял серию.”
- “Ты не справился.”
- “Нужно быть дисциплинированнее.”
- “Твой индекс счастья низкий.”

## Accessibility requirements

Проект должен быть удобен с screen reader.

Обязательные правила:

- semantic HTML;
- настоящие кнопки и формы;
- labels для input/select/textarea;
- понятные заголовки `h1`, `h2`;
- логичный порядок фокуса;
- не использовать только цвет для передачи смысла;
- после важных действий обновлять текстовое состояние;
- не делать критические элементы только иконками;
- не перегружать графиками;
- все данные графиков дублировать текстом;
- избегать сложных drag/drop;
- не делать auto-focus без необходимости.

## Security requirements

1. Никогда не доверять `Telegram.WebApp.initDataUnsafe`.
2. Всегда валидировать `Telegram.WebApp.initData` на backend через bot token.
3. Не хранить bot token в коде.
4. Использовать `.env`, `.env.example` без секретов.
5. Не логировать токены и полный initData, если там есть чувствительные данные.
6. API должен проверять пользователя на backend, а не только на frontend.
7. Данные пользователя должны быть доступны только ему.
8. Добавить базовый rate limiting позже, если появится публичный доступ.

## Performance requirements

Цель: один лёгкий процесс.

Правила:

- webhook вместо polling;
- scheduler не чаще одного раза в минуту;
- запросы к БД должны быть индексированы по `user_id`, `entry_date`, `due_at`;
- не сканировать всю БД каждую секунду;
- не делать heavy frontend bundle;
- не использовать SSR;
- static files отдавать просто;
- логирование без постоянного шума.

SQLite:

- включить WAL mode;
- включить busy timeout;
- предусмотреть backup файла БД перед production-использованием.

## Development rules for future agents

1. Follow `PLAN.md` unless Denis changes direction.
2. Do not add React/Next/Vue unless explicitly requested.
3. Keep implementation small and readable.
4. Prefer vanilla JS and semantic HTML.
5. Avoid speculative abstractions.
6. Do not add real payments or wallet custody without separate explicit approval.
7. Do not introduce AI recommendations until core loop works.
8. Validate with at least one smoke test after meaningful changes.
9. Keep imports at the top of JS files.
10. Do not widen scope into a general habit tracker.
